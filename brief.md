# Задание на методичку «Go Start» (часть 1 из 2): Go с нуля до среднего уровня

## 0. Как пользоваться этим файлом

Это **готовое задание для генерации методички**. Файл самодостаточный: ничего другого прикладывать не нужно. Исполнитель (ИИ-ассистент) пишет полную лабораторную работу по Go по плану из раздела 3, строго в формате из раздела 2, соблюдая правила из раздела 1.

Если ассистент не умеет выдавать готовый HTML-«бандл», он выдаёт **JSON** со схемой из раздела 2 (поля `units`, `sessions` и т. д.). Из такого JSON методичку собирает владелец проекта. Ссылки на внутренние файлы проекта (`bundle.py` и др.) исполнителю не нужны.

## 1. Кто читает и как писать

- **Читатель:** Laravel/PHP-разработчик, около 1,5 лет опыта. Знает ООП на уровне PHP, HTTP, SQL, Docker на базовом уровне, Git. **Go не видел никогда.** Строго типизированных компилируемых языков не писал.
- **Язык методички: русский.** Термины Go и код — как есть, при первом упоминании термин объяснён по-русски.
- **Главный приём: аналогии с PHP/Laravel.** Для каждого нового понятия коротко «в PHP/Laravel это было бы…» и чем Go отличается (интерфейсы без `implements`, ошибки как значения вместо исключений, структуры вместо классов, горутины вместо очередей/воркеров и т. д.).
- **Метод обучения:** сначала пробуешь сам, потом разбор. Не вываливать длинную теорию заранее. Каждый шаг маленький (15–90 мин), даёт видимый результат (вывод в терминале, тест, ответ сервера).
- **Показывать поведение запуском**, а не словами: специально сломанные примеры, вывод компилятора, `go vet`, `-race`, `pprof`. Каждый шаг заканчивается блоком «ожидаемый результат» (`result`) с реальным выводом.
- **Любое утверждение о коде — проверить запуском до того, как оно попадёт в методичку.** Все команды и весь код выполнить на чистой машине (macOS и Linux), записать реальный вывод. Нельзя придумывать вывод компилятора или версии. Если проверить нельзя, прямо пометить «не проверено запуском».
- **На «сложно» — упрощать**, а не добавлять деталей: аналогия, карта кода, схема. Блоки `deep` («Копнуть глубже») — отдельно и необязательные.
- **Версии-стандарт проекта:** PHP 8.4 (в сравнениях), PostgreSQL 18 (том монтируется в `/var/lib/postgresql`, **не** в `/data`), Redis 8, Docker Compose v2, Kubernetes 1.37 / kind v0.33. **Go: актуальная стабильная версия на день генерации** (проверить на go.dev/dl; ожидается 1.26.x или новее), в `go.mod` указывать её же. Все версии библиотек проверить на pkg.go.dev, закрепить в `go.mod`. Не использовать устаревшее (`ioutil`, `GOPATH`-режим, `interface{}` вместо `any` без причины).
- **Не писать:** пароли, токены, ключи; нерабочие ссылки (каждую ссылку открыть запросом до вставки); пересказ «Зачем» в блоках `deep` (они должны быть новыми по смыслу); эмодзи в теле текста (допустимы только ⚠️ в предупреждениях).
- **Осторожность на машине читателя:** тяжёлые прогоны (бенчмарки на минуты, нагрузочные тесты, сборка больших образов) помечать заранее — ноутбук греется. Docker запускается только когда нужен и описан шаг «как убрать за собой» (`docker compose down -v`, удаление образов).

## 2. Формат результата (схема данных)

Методичка — один объект `window.LAB`. Ключи верхнего уровня:

```
slug        строка, "go-start-lab" или "go-pro-lab"
title       строка, заголовок
subtitle    строка, 1–2 предложения: о чём лаба и что за проект
accent      цвет, например "#00ADD8"
planned     "~48 ч"
introHtml   HTML: вступление «что это, для кого, что получишь»
tocHtml     HTML: оглавление (сессии, разделы)
glossKey    key справочного раздела-глоссария (kind: "ref")
sessions    [{ n, title, dur, steps: ["step-1-1", ...] }]   — «сессия» = блок шагов на одно занятие, 3–7 часов
units       [ ... ]                                           — все разделы и шаги, плоский список
```

Элемент `units` — один из трёх видов (`kind`):

1. **`theory`** — теоретический раздел вне сессий: `{ key: "sec-N", kind: "theory", num, title, short, html, text }`. `html` — готовая разметка, `text` — тот же текст без тегов (для поиска). Поля `html` и `text` **всегда согласованы** (одно и то же содержание).
2. **`step`** — шаг сессии: `{ key: "step-S-N", kind: "step", num: "S.N", title, short, est: "~40 мин", session: "S", intro, result, why, deep, quiz, links, outro, html, text }`.
   - `intro` — что делаем (HTML, с кодом);
   - `result` — ожидаемый реальный вывод (`<pre class="out" data-lang="out"><code>…</code></pre>`) + пояснение, что значит «получилось»;
   - `why` — «Зачем это так»: решение и альтернативы, 3–6 предложений;
   - `deep` — список `{ summary, html }`: необязательные углубления (внутреннее устройство, редкие случаи);
   - `quiz` — 2–4 вопроса **на понимание**, а не на запоминание (строки);
   - `links` — `[{ u: "https://…", n: "что там", t: "название страницы" }]`, только проверенные;
   - `outro` — необязательно, одна фраза-мостик к следующему шагу.
3. **`ref`** — справочный раздел: глоссарий, шпаргалка «Go для PHP-разработчика», «частые ошибки», чек-лист. Формат как у `theory`.

Разметка внутри HTML: обычные `<p>`, `<ul>`, `<ol>`, `<table>`, `<code>`, `<b>`, `<a>`; блоки кода — `<pre data-lang="go"><code>…</code></pre>` (языки: `go`, `bash`, `yaml`, `sql`, `json`, `dockerfile`, `out` для вывода). Код экранировать (`&lt;`, `&amp;`). Каждый блок кода должен быть **полным и запускаемым** или явно помечен как фрагмент.

Требования к полноте:
- каждая сессия: 5–8 шагов; к каждому шагу `why`, `quiz` (≥2 вопросов), `links` (≥2), по возможности `deep` (≥1);
- перед первой сессией — теоретические разделы, которые нужны для сессий 1–3; дальше теория встраивается в `intro` шагов, а не копится отдельно;
- один **сквозной проект** на всю лабу (см. план), каждая сессия наращивает его; в конце каждой сессии проект собирается и проходит тесты;
- ключи (`key`) уникальны, все ключи из `sessions[].steps` существуют в `units`.

## 3. План: «Go с нуля до среднего уровня» (часть 1 из 2: «Go Start»)

**Параметры:** `slug: go-start-lab`, заголовок «Go Start: от нуля до уверенного middle» (репозиторий `meeymirita/go-start-lab`, папка `go-start`, файл методички `go-start.html`), сложность — средняя, `planned ~50 ч`, 12 сессий. Предварительные знания — только то, что в разделе 1. Следующая часть — «Go Pro» (`meeymirita/go-pro-lab`, от middle до senior) — продолжает эту, поэтому код сквозного проекта должен быть пригоден как её стартовая точка.

**Цель:** к концу читатель самостоятельно пишет на Go чистый, протестированный HTTP-сервис с PostgreSQL, понимает горутины и ошибки, читает чужой код, проходит собеседование уровня «Go middle».

**Сквозной проект «CoffeeGo»:** кофейня из других лаб проекта — каталог напитков, заказы, статусы. Сначала CLI-утилита, потом REST API на `net/http` и PostgreSQL, потом Docker и CI. Тот же домен, что в ООП-лабе на PHP (Coffee Shop API): читатель может сравнить решения.

**Структура сессий** (названия, содержание и основные шаги; исполнитель раскрывает каждую в 5–8 шагов):

1. **Первый запуск и инструменты (~3–4 ч).** Установка Go и проверка (`go version`, `go env`), «Hello» и `go run` / `go build` / `go install`, что такое пакет `main` и `func main`, `go mod init`, `go fmt`, `go vet`, чтение ошибок компилятора. Редактор (GoLand/VS Code + gopls). Чем компиляция отличается от PHP-интерпретации (один бинарник, кросс-компиляция `GOOS`/`GOARCH`). Первый CLI: аргументы `os.Args`, пакет `flag`.
2. **Типы и управляющие конструкции (~4–5 ч).** `var`, `:=`, нулевые значения, константы и `iota`, числа (размеры, переполнение), строки как байты, руны и UTF-8, `for` (единственный цикл), `if`/`switch`, `range`. Массивы и **срезы** (длина, ёмкость, `append`, разделяемая память: ловушка), `map` (порядок, `comma ok`, nil-map), указатели (`&`, `*`), `new`. Сравнение с массивами PHP.
3. **Функции и ошибки (~4–5 ч).** Несколько возвращаемых значений, именованные результаты, variadic, функции как значения, замыкания, `defer` (порядок, аргументы вычисляются сразу), `panic`/`recover` (когда нельзя использовать), **ошибка как значение**: `error`, `fmt.Errorf("%w")`, `errors.Is/As/Join`, sentinel-ошибки, свои типы ошибок. Сравнение с исключениями PHP: почему в Go нет try/catch.
4. **Структуры, методы, интерфейсы (~5–6 ч).** `struct`, вложенность и **embedding** (композиция вместо наследования), методы, получатель по значению и по указателю (когда что), экспортируемость по заглавной букве, интерфейсы без `implements`, `any`, type assertion и type switch, ловушка «nil-интерфейс ≠ nil-значение», `fmt.Stringer`, `io.Reader`/`io.Writer`, принцип «принимай интерфейсы, возвращай структуры». Сравнение с классами, абстрактными классами и trait в PHP. Первая версия домена CoffeeGo: `Drink`, `Order`, `OrderStatus` (аналог enum), правила переходов статусов.
5. **Пакеты, модули и структура проекта (~3–4 ч).** `go.mod`/`go.sum`, добавление и обновление зависимостей, `internal/`, `cmd/`, раскладка проекта (без культа «стандартной» раскладки), циклические импорты и как их избегать, `go work`, vendoring (когда нужен), приватные модули, `golangci-lint` и минимальный набор линтеров, `go doc`. Аналог Composer и PSR-4.
6. **Дженерики и стандартная библиотека (~4–5 ч).** Параметры типов, ограничения, `comparable`, `cmp.Ordered`, пакеты `slices`, `maps`, `cmp`; когда дженерики не нужны. `strings`, `strconv`, `time` (длительности, часовые пояса, ловушка форматирования `2006-01-02`), `encoding/json` (теги, `omitempty`, `Marshaler`, ловушки: `nil`-срез, неизвестные поля), `os`, `bufio`, `log/slog`, `embed`. Итераторы `range`-over-func (обзор).
7. **Тестирование (~4–5 ч).** `testing`, table-driven тесты и подтесты, `t.Helper`, `t.Cleanup`, `t.TempDir`, `testing/fstest`, `httptest`, бенчмарки (`b.Loop`), покрытие, **`-race`**, fuzzing, `testify`: когда стоит и когда нет, фейки вместо моков. Тесты домена CoffeeGo (все переходы статусов, граничные случаи). Аналог PHPUnit/Pest.
8. **Конкурентность (~5–6 ч).** Горутины (что дёшево, что нет), каналы (буферизованные, закрытие, `range` по каналу), `select`, таймауты, `sync.WaitGroup`, `Mutex`/`RWMutex`, `sync/atomic`, `context` (отмена, дедлайн, значения), `errgroup`, паттерн worker pool, типичные ошибки: утечка горутин, гонка данных, дедлок, захват переменной цикла (показать и починить). Каждую ошибку воспроизвести запуском и поймать `-race`.
9. **HTTP-сервер на `net/http` (~5–6 ч).** Handler и `ServeMux` (шаблоны путей и методов), JSON-API CoffeeGo (напитки, заказы), middleware (логирование, recover, request ID), валидация входа, единый формат ошибок, таймауты сервера, graceful shutdown, HTTP-клиент (таймауты, повторное использование, закрытие `Body`), `httptest`-тесты API. Сравнение с маршрутами и middleware Laravel.
10. **Базы данных (~5–6 ч).** `database/sql` и `pgx` (пул, контексты, закрытие `Rows`), PostgreSQL 18 в Docker, миграции (`goose` или `golang-migrate`), транзакции, `NULL` и `sql.Null*`/указатели, паттерн «репозиторий», подготовленные запросы, `sqlc` (обзор), SQL-инъекции, тесты с реальной БД (`testcontainers-go` или Compose). Сравнение с Eloquent/Query Builder и почему в Go обычно без ORM.
11. **Конфигурация, логи, Docker (~4 ч).** Переменные окружения (12-factor), валидация конфига при старте, `log/slog` (уровни, JSON, контекст), multi-stage Dockerfile, `scratch`/distroless, `CGO_ENABLED=0`, размер образа, healthcheck, `docker compose` (API + PostgreSQL 18), прогон миграций, `make`/`task`. Сравнение с Dockerfile для Laravel (php-fpm + nginx).
12. **Итоговый проект и приёмка (~4–5 ч).** Довести CoffeeGo: README, CI на GitHub Actions (`go vet`, `golangci-lint`, `go test -race`, сборка образа), `Makefile`, чек-лист «готово к ревью», самопроверка по «Go Code Review Comments», типичные вопросы собеседования с разбором (срезы, `nil`, интерфейсы, горутины, каналы, `context`, `defer`), сравнение итогового сервиса с версией на Laravel (код, размер, потребление памяти, время старта). Что дальше: ссылка на «Go Pro» (часть 2).

**Теоретические разделы (до сессии 1 и дальше по мере надобности):** «Зачем Go и чем он отличается от PHP» (компиляция, статическая типизация, один бинарник, GC, горутины), «Как устроен Go-проект и go-инструменты», «Карта изученного» (перед итоговой сессией).

**Справочные разделы (`ref`):** глоссарий; шпаргалка «Go для PHP-разработчика» (таблица: PHP-понятие → Go-понятие → ловушка); «50 частых ошибок новичка» (с кодом: что неправильно, что правильно); чек-лист ревью Go-кода; список полезных инструментов (`gopls`, `dlv`, `golangci-lint`, `air`, `staticcheck`).

**Чего в этой методичке НЕ делать** (оставить второй): профилирование и тонкая настройка GC, паттерны конкурентности выше worker pool, gRPC, OpenTelemetry, Kubernetes, `unsafe`/`cgo`, кодогенерация, разработка модулей Caddy.

## 4. Дополнительные материалы, которые нужно выдать вместе с методичкой

1. **Код сквозного проекта** — по сессиям (ветка или папка `session-N/` с итоговым состоянием после каждой сессии), чтобы читатель мог сверить своё решение. Весь код проверен: `go build ./...`, `go vet ./...`, `go test -race ./...` проходят.
2. **README лабы:** название, сложность, время, что получишь, предварительные знания, установка, строка «**Статус:** …» (что проверено запуском, что нет), структура сессий, ссылка на методичку, лицензия (код — MIT, тексты — CC BY 4.0).
3. **Список проверок:** какие команды и на какой ОС/версии Go реально запускались, что не удалось проверить.
4. **Список источников** (официальные: go.dev, pkg.go.dev, Go blog, Effective Go, Go Code Review Comments, Uber Go Style Guide, документация библиотек) с датой проверки.

## 5. Приёмка (исполнитель проверяет себя перед сдачей)

- Нет ни одного блока кода, который не запускался.
- Нет выдуманного вывода команд.
- Все ссылки открываются.
- Нет понятий, которые используются раньше, чем объяснены (проверить по порядку шагов).
- У каждого шага есть измеримый результат.
- `quiz` проверяет понимание: «почему так», «что будет, если…», а не «как называется».
- Ни одного секрета, пароля, личного пути (`/Users/…`) в тексте и коде.
- Объём сверен с `planned`: сумма `est` шагов сессии в пределах `dur`.
